- Reserva (N) → (1) Usuario: Una reserva pertenece a un usuario
- Reserva (N) → (1) Clase: Una reserva pertenece a una clase

3. ESTRUCTURA FÍSICA DE TABLAS (DDL)
================================================================================

-- Tabla: usuarios
CREATE TABLE usuarios (
    id BIGSERIAL PRIMARY KEY,
    username VARCHAR(100) UNIQUE NOT NULL,
    password VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Tabla: roles
CREATE TABLE roles (
    id BIGSERIAL PRIMARY KEY,
    rol VARCHAR(50) NOT NULL,
    usuario_id BIGINT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (usuario_id) REFERENCES usuarios(id) ON DELETE CASCADE
);

-- Tabla: clases
CREATE TABLE clases (
    id BIGSERIAL PRIMARY KEY,
    nombre VARCHAR(200) NOT NULL,
    descripcion TEXT NOT NULL,
    capacidad INTEGER NOT NULL CHECK (capacidad > 0),
    fecha_hora TIMESTAMP NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Tabla: reservas
CREATE TABLE reservas (
    id BIGSERIAL PRIMARY KEY,
    usuario_id BIGINT NOT NULL,
    clase_id BIGINT NOT NULL,
    creada_en TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (usuario_id) REFERENCES usuarios(id) ON DELETE CASCADE,
    FOREIGN KEY (clase_id) REFERENCES clases(id) ON DELETE CASCADE,
    CONSTRAINT uk_reserva_usuario_clase UNIQUE (usuario_id, clase_id)
);

4. CONFIGURACIÓN JPA/HIBERNATE
================================================================================

Archivo: src/main/resources/application.properties

Configuración relevante:
- spring.jpa.hibernate.ddl-auto=none  (DDL gestionado manualmente)
- spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.PostgreSQLDialect

Estrategia de generación:
- Las tablas se crean manualmente ejecutando el script SQL
- Hibernate solo valida el esquema (o no hace nada con ddl-auto=none)
- Los scripts de migración deberían usarse en producción

5. EJEMPLOS DE CONSULTAS FRECUENTES
================================================================================

-- 5.1 Obtener usuario por username con sus roles
SELECT u.id, u.username, u.created_at,
       ARRAY_AGG(r.rol) as roles
FROM usuarios u
LEFT JOIN roles r ON r.usuario_id = u.id
WHERE u.username = 'admin'
GROUP BY u.id;

-- 5.2 Listar todas las clases con conteo de reservas
SELECT c.id, c.nombre, c.descripcion, c.capacidad,
       c.fecha_hora,
       COUNT(r.id) as reservas_actuales,
       (c.capacidad - COUNT(r.id)) as cupos_disponibles
FROM clases c
LEFT JOIN reservas r ON r.clase_id = c.id
GROUP BY c.id
ORDER BY c.fecha_hora ASC;

-- 5.3 Obtener reservas de un usuario específico
SELECT r.id, c.nombre as clase_nombre,
       c.fecha_hora, c.descripcion, c.capacidad,
       r.creada_en as fecha_reserva
FROM reservas r
JOIN clases c ON r.clase_id = c.id
WHERE r.usuario_id = ?
ORDER BY c.fecha_hora ASC;

-- 5.4 Verificar si un usuario ya reservó una clase
SELECT EXISTS (
    SELECT 1 FROM reservas
    WHERE usuario_id = ? AND clase_id = ?
) as ya_reservado;

-- 5.5 Obtener usuarios con rol ADMIN
SELECT u.id, u.username
FROM usuarios u
JOIN roles r ON r.usuario_id = u.id
WHERE r.rol = 'ADMIN';

-- 5.6 Clases próximas (próximas 24 horas)
SELECT id, nombre, fecha_hora, capacidad
FROM clases
WHERE fecha_hora BETWEEN NOW() AND NOW() + INTERVAL '24 hours'
ORDER BY fecha_hora ASC;

-- 5.7 Eliminar reserva (propagación en cascada verificada)
DELETE FROM reservas WHERE id = ?;

6. CONSIDERACIONES DE SEGURIDAD
================================================================================

1. Contraseñas:
   - En producción, las contraseñas DEBEN estar hasheadas (BCrypt recomendado)
   - El scriptincluye placeholders para contraseñas hasheadas

2. JWT Secret:
   - Configurado en application.properties como variable de entorno
   - Nunca hardcodear en el SQL

3. Acceso a datos:
   - Usar prepared statements para evitar SQL injection
   - Validar permisos por rol en la capa de servicio

4. Pool de conexiones (Supabase/PostgreSQL):
   - maximum-pool-size=2 (limitado por Supabase gratis)
   - En producción ajustar según necesidades

7. MIGRACIONES Y VERSIONADO
================================================================================

Estrategia recomendada:
1. Usar Flyway o Liquibase para migraciones en producción
2. Nombrar scripts: V1__creacion_tablas.sql, V2__agregar_indices.sql
3. Mantener este script como referencia inicial
4. NO modificar tablas en producción sin migración controlada

Ejemplo de migración con Flyway:
   V1__creacion_tablas.sql        → Este archivo
   V2__agregar_columna_edad.sql   → Nuevas versiones

En caso de cambios:
   - Agregar columnas: ALTER TABLE ... ADD COLUMN ...
   - Crear índices: CREATE INDEX ...
   - NO eliminar columnas sin validación

9. NOTAS ADICIONALES
================================================================================

• Todas las tablas tienen created_at para auditoría
• updated_at se actualiza automáticamente via trigger
• ON DELETE CASCADE asegura limpieza automática de datos huérfanos
• UK (usuario_id, clase_id) evita reservas duplicadas
• Use CHECK para validar capacidad > 0
• Los índices mejoran performance en búsquedas frecuentes
• PostgreSQL autovacuum debe estar habilitado en producción
